# Handoff — 2026-08-27 (current)

## Read this first

The Lieder scan corpus is not safe to train or evaluate against yet. Manual review
and a content audit confirmed two systematic label defects:

1. `extract_stage2_pairs.py` zipped scanned systems to MuseScore/OpenScore systems
   by flat ordinal position. OpenScore adds explicit line breaks, while MuseScore
   may add still more during layout. One printed scan line can therefore correspond
   to two reference lines; the ordinal pairing then shifts later labels.
2. `recover_excluded_pairs.py` used the upstream recognizer's matched note span as
   the output boundary. A three-bar crop could receive only the one bar the model
   confidently matched. Those labels are also circular for evaluation because the
   same upstream model family is the benchmark baseline.

**Do not resume labeling the old truncation set and do not start vocal training.**
Finish the rebuild below, then adjudicate the new 100-item `Rebuilt alignment` set.

## Evidence behind the decision

- The user's saved note on `IMSLP183800-sys13-v0` was recovered from Chrome
  localStorage: the scan has three bars while the label has only the last bar.
- Seven of the first eight reviewed truncation cases were recovery-generated.
- 44/54 truncation suspects were recovered pairs, versus only 3/12 controls. The
  old review set was strongly source-biased.
- Held-out cohort signature: ordinary pairs had more upstream bars than label in
  10/236 (4.2%); recovered pairs in 44/126 (34.9%).
- Content alignment of ordinary held-out pairs found 79/146 trusted crop/label
  disagreements. In 39, both source alignments were perfect but pointed to
  different measure ranges. In 27, the crop matched another system's label exactly.
- In `IMSLP183800`, two narrow illustration detections preceded the real score,
  shifting all ordinal pairs by two. Real systems map cleanly once those detections
  do not consume score music.
- Removing recovered pairs increased the ours-vs-upstream delta, but does not make
  the ordinary subset publishable; it still contains shifted passages.

## Addendum — the 07:48 recount produced nothing (found 2026-08-27, later)

The "12 shards running, 2 completed" state described above was not partial progress.
It was a total loss, and the two completed shards were empty.

**What actually happened.** All 12 shards were launched in the same second
(07:48:07). Each ONNX Runtime process sizes its thread pools from `nproc` (128) and
holds **206–307 threads**; the container's cgroup limit is
`/sys/fs/cgroup/pids.max = 3840`, with ~1000 threads already resident. The startup
burst hit the pid ceiling and `pthread_create` returned EAGAIN:

```
onnxruntime/core/platform/posix/env.cc:186 ... pthread_create failed,
error code: 11 error msg: Resource temporarily unavailable
```

Two distinct consequences:

1. **130 of 330 scores (39%) were dropped.** The per-score `except Exception` in
   `compare_bar_counts.main()` printed `FAILED` and continued, so the run neither
   aborted nor exited non-zero. Shards 06 and 08 lost all 27 of their scores each,
   wrote `bar_count_rows_v2_06.json` / `_08.json` as `[]` (2 bytes), and **exited 0** —
   indistinguishable from success without reading the logs by hand.
2. **The 10 surviving workers deadlocked.** They were not slow, they were stopped:
   all 307 threads in state `S`, main thread in `futex_wait_queue`, **0 CPU ticks over
   a 10-second sample**, 0.3–2.8% CPU after 12 minutes, and no log output for 12
   minutes. ONNX Runtime was blocked waiting on pool workers that were never created.
   **Zero scores completed successfully across the entire run** — `grep -E
   "^IMSLP[0-9]+: [0-9]+/" bar_count_v2_*.log` matches nothing.

**Why this was dangerous, not merely wasteful.** Had the finish sequence above been
run as written, `jq -s 'add'` would have merged a ~60%-complete rows file,
`align_lieder_systems` would never have seen the missing scores, and everything
invisible to it would have been quarantined. The output would have read as the
alignment being appropriately conservative — a smaller clean corpus — rather than as
lost data. That is the same failure shape as the truncation defect this rebuild
exists to fix.

**Fixes applied** (`training/omr_datasets/compare_bar_counts.py`, the only source file
this recovery touched):

- New `--failed-out PATH`: every uncomparable score recorded as JSON, not left to be
  grepped out of a log.
- A `scores failed: N` line, and `scores compared:` now excludes failures.
- **Non-zero exit whenever any score failed.**
- `--rows-out` is refused when the row set is empty, so a shard can never again leave
  a 2-byte `[]` that a merge glob reads as a completed shard.
- `tests/test_compare_bar_counts.py` covers both: a failed score is recorded and exits
  1; an all-failed run writes no rows file. 20/20 focused tests pass on the instance,
  including the stale-margin case the section above listed as failing (the resync
  cleared it).

**Relaunch.** `/workspace/b0/lieder-rebuild/relaunch_recount.sh` reruns all 330 scores
at **4-way concurrency with a 45s stagger** (4 × ~310 ≈ 1240 threads, well under
3840), moves the dead run's artifacts to `failed_run_20260827_0748/`, and refuses to
start if a recount is still running. It cannot run until the hung PIDs are killed.
