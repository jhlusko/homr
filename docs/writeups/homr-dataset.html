How the scan-aligned training data was created

This note documents provenance and quality controls for the scan-adapted recognition data. It is not a claim that every source label is perfect. Its purpose is to make the remaining assumptions inspectable and to explain why alignment was treated as a modelling problem rather than a file-copy operation.

The Arm A recipe retains OSSQ and v4 Lieder scan data and uses PDMX-only replay. This is a deliberate mixture choice: prior experiments adding large synthetic-render replay directly to a scan-adapted model reduced scan accuracy at every tested weight.

The failure that made rebuilding necessary

The original OSSQ pipeline paired a crop with symbolic material using page and system indices. The images came from scans; the symbolic segments followed synthetic pagination. The two versions can have different page breaks while retaining enough similar system counts for the join to look valid. Basic guards passed: a record existed, part counts matched, and the token stream parsed. The semantic pair was nevertheless wrong.

The key diagnostic was qualitative: a model reading matched the scan exactly while disagreeing with the assigned target. That establishes a label join failure, not a model failure. A focused human audit of 52 worst post-fix pairs found zero mismatched pairs.

Reconstruction and independent checks

  1. Start from whole-score MusicXML rather than the lossy segmented token artifact.
  2. Recover staff-local symbolic streams with positional joins, preserving clefs, barlines, and repeat barlines that segment round-tripping had dropped.
  3. Align scan systems and symbolic systems using visual bar-count/geometry evidence.
  4. Independently compute reverse fingerprint alignment from recognition readings and the candidate symbolic streams.
  5. Use agreement as a high-confidence evaluation set; route disagreement, phantom, rejected, and ambiguous cases to separate review queues rather than silently assigning a target.
  6. Render both target notation and scan crop in a browser review surface. Review labels include correct, wrong, truncated, shifted, and notes; this makes failure modes visible that token metrics hide.

The two aligners have different failure modes. Geometry is vulnerable to unusual barline layouts and cropping; reverse matching is vulnerable to systematic recognition errors and one-to-many line breaking. Agreement is therefore evidence, not merely a convenient filter.

What review changed

Reviewers found three classes of defects that were easy to miss in aggregate accuracy:

  • Line-break multiplicity. A scanned line can correspond to two reference lines when the source inserts a break that MuseScore does not condense. These must be identified and merged rather than called model substitutions.
  • Displacement. A correct local pattern shifted by one or more events can make all downstream tokens look wrong. Reverse matching catches many, but it is not a proof against every systematic offset.
  • Truncation and stale vocabulary. A target may terminate early, or tokens absent from a checkpoint-era vocabulary can shift later positions. Both invalidate naïve exact-match interpretation.

Clef loss (2.4% of staves) and missing barlines/repeats were also repaired. Absolute pitch scoring had hidden the clef problem entirely; rendering was the necessary test.

Quality boundaries

What the dataset does not claim: OCR-derived text boxes are incomplete by construction; a box exists only if OCR and score text agree. A model detecting text OCR missed can be correct yet count as a false positive. Similarly, staff-level consensus reduces alignment risk but does not make accepted pairs ground truth in a historical-editorial sense.

Dataset cleaning is not automatically a source of score gains. Several genuine, small defects (unison duplicates, stale numerator tokens, and an overfull-row rule) were individually below 1% of affected tokens and did not move accuracy reproducibly. The large, measured correction was scan/reference alignment. The clearest remaining distributional mismatch is tuplet frequency: 1.78% of notes in the training corpus versus 6.58% in OSSQ.

Reproducibility checklist

  1. Keep raw scans, whole-score source, derived streams, alignment decisions, and review verdicts separately versioned.
  2. Never recompute an evaluation target with a model whose score will be reported against it.
  3. Record the token vocabulary used by every checkpoint; compare streams only after normalising known vocabulary differences.
  4. Sample and render extreme metric changes before attributing them to training.
  5. Report support and confidence intervals. A rare symbol gain without held-out support is a hypothesis, not a feature.
  6. Keep scanned evaluation, rendered replay, and vocal evaluation separate; an aggregate can hide a domain regression.
