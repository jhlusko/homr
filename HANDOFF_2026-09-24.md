## 2. The OSSQ stem rebuild — `build-20260924-stems`

**The defect.** The published OSSQ corpus (`ossq-scanned-v1`) has **no stem labels**: every
note reads `unknown`. The source has them — MuseScore's export of `sq7541288` carries 10,115
`<stem>` elements, its cleaned MusicXML 10,111 — but the per-system MusicXML homr builds
sidecars from had zero.

**The cause.** In OSSQ's vendored preprocessor, `convert_musicxml_to_lmxe.py` wrote the LMXE
and the per-system MusicXML from the same object, and `strip_stem_directions()` mutates it in
place. The strip is meant for the LMXE text format only. The MusicXML was delinearised after
it, so it lost every stem too.

**The fix** — `ossq-omr-data` **`c10725b`**, pushed. Writes the MusicXML before the strip.
Verified on `sq7541288`: **141/141 LMXE byte-identical** to the existing build, per-system
MusicXML **0 → 10,111 `<stem>`**. Follows the repo's patch convention:
`vendor/patches/musicxml-keep-stems.patch`, `vendor/STEM_PATCH.json` (before/after hashes),
`tools/check_stems.py` (asserts the call order from source; **confirmed to fail on the
unpatched file**), `make check-stems`.

**Why nobody noticed.** The other agent's `rebuild_ossq.py` never runs the LMXE stage — it
inherits pre-built, stem-stripped MusicXML from the source tarball. And a missing stem is
masked, so it trains nothing rather than raising.

**The rebuild.** `/root/rebuild_stems.py`, log `/root/rebuild_stems.log`, markers in
`/workspace/ossq-build/build-20260924-stems/`. Mirrors `rebuild_ossq.py` exactly — same
interpreter (`/workspace/venv-ossqbuild-26`), `PYTHONPATH`, homr checkout, conversion args —
so the patch is the only variable. It:

1. refuses to start unless `check_stems.py` passes;
2. copies the source to `/workspace/ossq-build/ossq-omr-stems` (the original stays intact);
3. re-runs `convert_musicxml_to_lmxe` for the 96 scanned scores, then **asserts every LMXE is
   byte-identical** to the original tree and the segment set is unchanged;
4. re-runs alignment (which *copies* `musicxml/unaligned` → `scanned/systemwise`, so the fix
   propagates) and `convert_ossq` for train/valid;
5. prints `REBUILD_DONE`. It is resumable via `DONE_*` markers.

It does **not** re-run any YOLO or image stage — none depends on stems. It never touches
`build-20260923`, which the `mixed` run is reading.

**One environment change, recorded:** the LMXE stage needs `tokenizers`, absent from
`venv-ossqbuild-26` because that stage had never run there. Installed after a dry run showed it
purely additive: `tokenizers 0.23.2`, `huggingface-hub 1.32.0`, `hf-xet 1.6.0`, `click 8.5.0`.
Nothing existing changed.

## 3. What steps 1 and 2 found: PDMX-only heads, rules on the same examples

Rules were scored on **exactly** the examples each evaluation scored (from its
`predictions.jsonl`), so head and rule share one population. Outputs:
`/workspace/train-20260923/heads-pdmx-v6/eval-*/`, `/workspace/train-20260923/rules/`.

| | PDMX | Lieder | OSSQ scanned |
|---|---|---|---|
| beams, exact vector | .862 | .710 | **.900** |
| beam rule, paired per note | — | — | rule **81.9%** vs head **90.8%** |
| slur side, head macro-F1 | .818 (n=3,585) | .570 (n=45) | .840 (n=6,081) |
| slur-side rule | **.819** | .321 | not computable — no stems |
| ties, head macro-F1 | .860 | .705 | .746 |
| tie rule precision | 11.5% | 7.8% | 15.1% |
| tie constraint (same pitch) | 96.7% | 95.3% | 100.0% |
| stems | .807 | .812 | no labels |
| slur span F1 | .761 | .482 | .851 |
| advance, nontrivial | .790 | .853 | .808 |
| dynamics | .100 | .124 | .099 |

**Beams on scans: the head beats the rule, paired.** On 23,676 OSSQ notes it recovers 79.2%
of the rule's mistakes (3,400 notes) and loses 6.6% of its agreements (1,283) — net +8.9
points. That contradicts the roadmap's "default to the rule everywhere", which rested on the
head at 69.1% on scans. **Not yet a ship decision**: the roadmap's named gate is precision on
*rest-spanning* beams specifically, which this doesn't isolate, and the 69.1% came from an
older corpus and head — the jump needs explaining before it is trusted.

**Ties earn their keep everywhere** — the best-supported head result so far.

**Slur side is undecided.** The only well-powered comparison is a tie (.818 vs .819). Lieder
favours the head but on 45 slurs. OSSQ can't be scored until the stem rebuild lands — that is
the other reason §2 matters.

**The domain gap is Lieder, not scans.** PDMX-only heads do better on OSSQ than in-domain on
PDMX, and fall off on Lieder (slur span .482). The mixed run's ×3 Lieder weighting is the lever.

**Dynamics is broken everywhere.** Keep it disabled.

### Tool coverage, and one gap

`rule_vs_head.py`, `derived_stems.py` and `stem_arbiter.py` locate MusicXML under the OSSQ
source layout (`scores/*/*/musicxml/unaligned/`), so **beam and stem rules run on OSSQ only**.
PDMX and Lieder have no per-window MusicXML segment to join. Building one is a new join, and
joins are where this pipeline has repeatedly gone wrong — do it deliberately, not in passing.

`slur_side_baseline.py` reads sidecars; **`tie_baseline.py` reads token files** — link both, or
it reads 0 notes and reports nothing, which my first pass did.
